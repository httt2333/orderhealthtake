# 安心药盒｜AI 药单变化理解助手

**正式 PRD V1.0 · Codex 开发交接版**  
版本日期：2026-10-16  
项目性质：AI 产品研究与策划笔试的 **响应式 Web Demo**（手机优先，兼容平板与桌面）；不是实体药盒，也不是医疗器械或临床决策系统。  
状态：**方案冻结候选 / 尚未完成目标用户实测**。本文把已有调研证据与新提出的产品需求分开。  
主角色：独立生活、长期用药的老年人；协作角色：家属/可信协助者；医生/药师仅在线下或既有专业系统中负责医疗确认，本 Demo **不模拟医生签署或诊疗**。

# 0\. 五分钟读懂本产品（Codex 必读）

**一句话定义**：当医生调整了老人的既定用药安排，家属可协助上传并校对新旧资料；AI 帮助识别非结构化药单、规则程序比较明确的字段差异；老人通过**语音＋大字图形卡片**逐项理解“哪里不一样、哪里还不确定、接下来该向谁核实”。

**首页要回答的用户问题**：**“医生给我换药了，我怎么看懂哪里变了？”** 而不是“今天吃药了吗？”

**核心价值**：减少老人在看小字、搜索旧记录、逐条比对和理解专业信息时的负担；不承诺降低实际误服率或替代药师的药物核对（Medication Reconciliation）。

**第一版成立条件**：  
1\. 老人可以不自己拍照、不理解 OCR/Prompt，通过少数大按钮或语音入口完成 **听变化→逐项看→获取待核实清单**。  
2\. 家属可以独立完成 **录入旧资料→上传/导入新版资料→校对机器识别字段**；任何真实用药方案修改权不属于家属或 AI。  
3\. 实际代码有清晰的 **AI 提取适配层** 与 **确定性 diff 引擎**，若未接入模型则诚实显示“示例资料/模拟解析”，不能宣称已经使用真实 AI。  
4\. **停用、替换、剂量改变、起效日期等高风险信息** 必须保留原文证据和来源；无法明确时输出“待专业核实”，不得根据药物从新版清单消失而擅自判定“停药”。  
5\. 端到端 Demo 存在**正常、资料不全、矛盾、识别失败、语音失败、拒绝家属协助**等可复现路径，不只是静态页面。

**不是本项目**：自动处方、健康问诊、识别药丸即推荐剂量、远程监控是否真正吞服、药物相互作用诊断、实时药房/医院 API 对接、自动控制硬件发药、泛健康 Chatbot。

# 1\. 决策背景与证据/假设边界

## 1.1 已作出的产品决定（用户已确认）

• 任务场景：题设 **A**，约 68 岁、独立生活、长期服用多种处方药的老年人；E 短期疗程不作为本次 MVP。  
• 优先问题：**医生改变既定用药计划之后，老人如何理解新旧资料差异、确认哪些项目需要核对，并避免继续沿用可能过期的管理记录。**  
• 平台限定：**网页 / 手机浏览器**。不开发真实药盒、RFID、相机支架或物联网设备；可用纸质药盒的示意插画表达管理场景。  
• 角色方案 B：**老人自主使用、家属辅助初次录入与拍照/上传**；家属不能代替医生决定方案。  
• 交互偏好：**语音与自然对话优先**，搭配大按钮、图标、颜色与少量大字；不强制老人掌握拍照和多层 App 菜单。  
• 设计策略：先做完整任务链路、多页面可测试原型，再决定是否扩张为真实服务。

## 1.2 现有研究支持什么（非最终效果证明）

• MEMORABLE：多药管理包括获取、开始或变更、持续、复核等连续活动；方案变化会影响既有的用药习惯。来源：[https\://pmc.ncbi.nlm.nih.gov/articles/PMC7272211/](https://pmc.ncbi.nlm.nih.gov/articles/PMC7272211/)  
• 老年多药药单变更，尤其出院衔接时可能出现错误；某项针对 151 名特定出院患者的研究报告，出院7天时 39% 发生研究定义的至少一项用药错误。**不能外推成所有居家门诊老人的比例。** 来源：[https\://pmc.ncbi.nlm.nih.gov/articles/PMC12638008/](https://pmc.ncbi.nlm.nih.gov/articles/PMC12638008/)  
• 不同模拟装药实验对错误的测量与结果差异大：一项 27 人实验发生分装错误比例较高，另一项 50 人实验填装正确率较高。不能因此宣称所有老人每周最费时间的一定是分装。来源：[https\://pubmed.ncbi.nlm.nih.gov/28872038/](https://pubmed.ncbi.nlm.nih.gov/28872038/) 、[https\://pubmed.ncbi.nlm.nih.gov/21486736/](https://pubmed.ncbi.nlm.nih.gov/21486736/)  
• 部分老人使用日常场景、实体药盒和固定位置形成服药记忆线索；复杂数字界面可能不符合其现有习惯。**这支持探索适老交互，但没有证明本网页语音方案有效。** 详见前述调研档案。  
• 市场竞品中，Hero、MedaCube、EllieGrid、Karie 等更侧重硬件出药、装药结构和长期护理；Medisafe、MyTherapy 提供软件提醒。我们的切口不是再次复制“定时提醒”，而是**药单更新前后的信息理解与核对准备**。来源见竞品档案。

# 2\. 目标、范围及成功判定

## 2.1 P0 用户目标

• 老人：听得懂变化；不必学习文件上传；随时知道下一步；能复听、返回、求助；不会被引导擅自改药。  
• 家属：能够校对提取信息和资料来源；知道哪里出现冲突；能把待核实问题清单交给专业人员。  
• 评审：清楚看到“原始资料→AI提取→人工校对→规则比较→语音图形解释→待核实清单/历史”的真实闭环，能切换正常和失败案例。

## 2.2 产品指标与演示验收指标（都是**预设验收目标**，非研究结果）

**工程验收**：预置虚构案例下，所有必经页面/分支可达；关键字段有证据出处；错误不会静默跳过；重新加载后可恢复本地案例进度；模拟与真实 AI 运行模式有清楚标签。

**研究时拟采集**：总任务时间、字段校对错误、遗漏重要变化、能否识别冲突、老人独立操作比例、语音失败恢复率、求助次数、主观负担。先不设不实的用户行为提升目标。

## 2.3 P0 / P1 / 非目标

类别　｜　内容  
**P0 必做**　｜　双角色入口；老人欢迎页、语音/按钮启动、解释页、变化卡、求助、待核实清单与历史；家属资料管理、上传/示例载入、AI提取校对、对比审核；本地案例状态；适老化与失败路径；模拟案例；至少核心AI抽取接口的可接入实现；规则diff测试  
**P1 有余力**　｜　浏览器语音识别可选输入；导出打印优化；可调整字体/语速；资料缺失补录；家属协助邀请/取消；无真实账号的双端同步体验模拟  
**不做**　｜　实体药箱、IoT控制、处方开具或确认、自动药物替换/停药、AI临床建议、实时服药提醒/打卡、医院HIS对接、真实支付、真实医院/医师账号体系、疾病风险诊断、社交社区

P0 的重点是**把一个任务做深**，而不是做一百个空页面。

# 3\. 用户角色、权限与画像

## 3.1 P1 老人｜主操作用户

• 模拟画像：张叔叔，68岁，自己住，已有多年用药习惯，5种长期药物，使用普通分格药盒，主要通过微信、视频等使用手机；对拍照上传或小字菜单可能不熟悉。**这些是为原型统一场景设定的假设，不是实际采访对象。**  
• 触发事件：近期医生调整某项用药安排，老人想知道“哪里变了”；平日不强制使用产品。  
• 目标：用少量操作听懂变化并保留独立性。  
• 阻力：小字、精细点击、陌生术语、分支过多、误触后无法返回、需要记住口令、对机器结果过度信任。

## 3.2 P2 家属/可信协助者｜辅助资料管理员

• 典型行为：为老人上传旧版已记录用药清单和新版书面资料，纠正OCR错字，标记来源日期，查看需核实问题，交给医生或药师询问。  
• **权限范围**：编辑“资料转录文本”、记录来源，**不具有专业确认权**；不得修改“AI已经确定医生同意”的虚假状态。  
• 演示阶段角色切换不需真实账号，仅用明显的角色标题/底色与“进入老人端/进入家属端”按钮；正式产品则必须有独立权限、邀请/撤销与审计日志。

## 3.3 P3 医生/药师｜产品外部的专业确认者

• 不拥有 Demo 后台、登录页或“审批”按钮。  
• 真实世界里负责解决医嘱冲突和最终确认正确方案。系统仅生成 **供专业人员核实的问题清单**，不把用户自行勾选等同于专业签署。

# 4\. 完整任务旅程与状态机

## 4.1 首次使用

1\. 老人进入首页，选择“医生给我换药了”；听到简短语音与字幕，不需要说明“AI模型”是什么。  
2\. 检查是否有可比对的旧版已记录资料；没有则进入“请家人帮忙准备资料”。  
3\. 家属切换到协助工作区，录入旧资料，再导入新版资料：**照片/文件或一键载入官方演示用虚构样例**。  
4\. AI 或明确标记的模拟解析器提取药名、剂量、频率、时间、备注和资料日期，逐字段关联出处。  
5\. 家属核对**机器转写与原始纸本是否一致**；这并非医疗有效性核对。模糊/冲突字段不允许悄悄“确认正确”。  
6\. 确定性差异引擎比较新旧字段，生成变化概览与“需专业核实项”；**不更新真实有效服药安排**。  
7\. 老人逐卡听说明，可以重听、暂停、看出处、点“听不懂”、叫家人。每一页“下一步”明确可见。  
8\. 结束时输出“资料变化小结＋待问医生/药师的问题”，提供分享/打印；历史中明确标注“已查看，但仍待专业核实”。

## 4.2 下次回来

• 首页显示“上一次资料核对：日期、状态、待专业核实数量”与“重新听一遍”。  
• 新一次医生调整：复制上一条**资料记录作为对照来源（须核对版本和日期）**，并导入新的书面资料；不得静默用上次AI推断结果充当权威旧处方。

## 4.3 内部 case 生命周期（不等于医嘱生效状态）

CREATED → SOURCES\_PENDING → EXTRACTING → TRANSCRIPTION\_REVIEW → READY\_TO\_COMPARE → DIFF\_READY → ELDER\_REVIEWING → SUMMARY\_READY → ARCHIVED

可从任意非归档节点进入 BLOCKED\_NEEDS\_CLARIFICATION（资料冲突/缺失/不可辨）或 TECHNICAL\_FAILURE，后者允许重试或使用显式标注**的虚构示**例继续演示。

**两套状态严格区分**：  
• 资料处理状态：unreviewed / transcription\_checked / needs\_source\_review；“checked”只代表与上传的文字/照片一致。  
• 医疗有效性状态：not\_verified\_by\_professional / user\_reports\_professional\_review（仅为用户陈述）/ externally\_verified\_evidence\_provided（如需未来版本，须留证据与核验流程）。MVP默认全**部为第一个，绝不自动跃迁到“已由医生确认”。**  
**• 若无法**确认新版文档完整性、适用日期或用药身份，允许**显示资料差异**，但必须给出“不适合据此改变用药”警示。

## 5.2 关键页面详规

### W00｜欢迎与演示入口

• 首屏主句：“医生换药了，哪里变了？我们陪您一项一项看。”  
• 显著区分 **我是用药人** / **我是帮助家人的人**；第三入口“查看演示场景”（评审）。  
• 页面不要用“智能硬件控制”“药物自动诊断”等容易误导的表达。

### E01｜老人首页

• 主 CTA：“医生给我换药了”（大图标＋大字＋可朗读）；次 CTA：“听上次的核对结果”。  
• 少量状态：上次核对日期、是否还有待问医生/药师的问题。没有数据时用单句解释“还没有核对记录”。  
• 首屏最多两项主要操作，底部固定“找人帮忙”；无复杂功能宫格。

### E02｜发起任务 / 语音导引

• 默认开场字幕：“您可以直接说，也可以按下面的按钮”。两大意图：**医生给我换药了**、**我想听以前的记录**。  
• **语音输出 TTS 为 P0**，语音输入 STT 为 P1，是否支持由设备浏览器决定；不自动开启麦克风。  
• 错误意图/无法识别：给出候选大按钮确认，不陷入无穷追问；不要让开放聊天输出医疗建议。

### E03｜等待家属准备

• 展示：已有旧药单/需要新资料/尚待OCR检查三种清晰状态；“我不会拍照怎么办” → “让家人帮忙”。  
• 提供角色切换链接（Demo专用）而非真实发送短信或虚假“已通知家属”。  
• 用户离开或网络异常后回来不丢掉已完成进度。

### F01｜家属工作台

• 卡片1：当前核对任务；卡片2：旧资料和新资料状态；卡片3：尚待核对字段；卡片4：待咨询医生/药师的问题。  
• 不做健康指标、日常吞服率和家属监控面板。

### F02｜资料导入

• 明确**旧记录和新资料各一份**，显示来源类型、日期与是否完整，禁止只上传药盒照片就声称得到有效医嘱。  
• 接受常见 JPG/PNG/WebP/PDF 或文本粘贴（P0至少实现图像＋手动文本/样例；PDF如受工程限制须清楚显示未支持）。文件大小与类型在UI说明；不支持时友好报错，不崩溃。  
• 提供拍照上传、选择文件、手动输入、**使用示例药单**；示例必须是虚构药名，不出现真实处方。  
• 有来源与日期字段；仅从药品包装读取的信息标注“药品信息，不能替代医嘱”。

### F03｜AI提取与转录核对（整个项目最重要的家属页）

• 左侧/顶部保留**原始资料图片或文本**；右侧/下方是字段表（药物名称、剂量/单位、频次、时点、起止日期、备注）。手机堆叠，桌面并列。  
• 每个字段附来源片段和置信提示（不得把随意浮点数伪装为临床概率）；“我看到原文并校正了转录”是逐字段/逐条确认。  
• 检出文本模糊、缺药名、单位不明、同名规格冲突：标记并继续要求核实，不允许“确认全部正确”绕过。  
• 显示运行模式：“真实AI提取”或“预置示例解析”；失败时可重试/改手工，不静默切到模拟。

### F04｜差异比较与待核实项预览

• 仅在足够结构化、已转录校对的基础上比较；分类：changed、explicit\_added、explicit\_stopped、unchanged、ambiguous、missing\_in\_new。  
• **关键规则**：missing\_in\_new \= “新资料未提及，无法判断是否停用”，不是 explicit\_stopped。  
• 重点显示“冲突/不完整/日期不明”；不能让家属把专业核实状态一键改成“医生已确认”。  
• 输出供老人听懂的结构化卡片，不允许把仍存在冲突的草稿变成确定服药安排。

### E04｜变化总览

• 首屏不展示密集药名表：例如“资料有2处不一样，另有1项需要请医生/药师确认”。  
• 大图标区分“资料发生变化”“需核对”，颜色只是辅助；短句语音说明后进入逐项。  
• 绝不使用“已为您调整用药”“用药已安全更新”。

### E05｜逐项变化卡（核心展示页）

• 一张卡只处理一项药物差异；顶部“第 1 项/共 N 项”；中间是**旧资料 vs 新资料**，例如模拟药A：早上→晚上。  
• 变化类型图标＋文字；原文证据可展开；危险信息必须可朗读，但可选择静音保护隐私。  
• 三个主动作：**再听一次 / 下一项 / 我没看懂（求助）**；同时允许“上一项”。  
• “我听明白了”只代表阅读状态，**不作为真实执行或临床确认**。

### E06｜需要帮助

• 明确给出问题：“资料中哪一项需要医生或药师核实？”  
• 可以选择“给家人看看”“查看待核实清单”“返回重听”。Demo不直接拨打真实电话、不声称医生在线。  
• 用户说“那我今晚怎么吃/是不是停药”等应转至安全提示：“我不能判断，请根据医生给出的有效安排联系医生/药师核实；如担心立即用药安全，请直接联系当地专业医疗服务”。避免给出剂量建议。

### E07｜核对小结／问题清单

• 分为：已读懂的**资料变化**、尚未澄清的**问题**、每项对应的文档出处和时间。  
• 默认标题“资料变化小结（不作为用药指令）”。提供“复制/打印/浏览器分享”中的可用方案，分享失败可手动复制，不假装已发给医生。  
• 不出现绿色大章“已安全完成医嘱变更”；仅说明“信息已整理，相关事项待专业核实”。

### E08｜历史记录

• 每条历史显示“资料比较日期 / 来源日期 / 几处变化 / 几项需核实 / 老人是否听过”，并可打开旧小结。  
• 不是服药历史，不记录吞服率。浏览器存储丢失时要解释“演示记录仅保存在本设备”。

### E09｜适老设置（P1）

• 字号：标准 / 更大；语速：较慢 / 标准；朗读：开启 / 关闭；高对比与静音；每一项有示例且可恢复默认。  
• 即使设置未完成，系统默认字号、按钮和对比度已经适老。

### D01｜评审情境切换

• 预置正常/遗漏/冲突/语音失败/家属未准备好案例，清晰选择和重置，避免要求评审手工输入十几条药物才看到价值。  
• 此页明确“测试控制台，不面向真实老人”；不破坏真实产品叙事。

# 6\. 端到端产品故事 / 用例

## UC01 正常核对（P0，Demo主线）

**前置**：旧版模拟资料已记录；新版模拟医生资料可导入，来源和有效日期清楚，家属逐项确认转录。

**步骤**：张叔叔首页发起 → 语音提醒请家属准备 → 家属加载两份演示资料 → AI/规则解析 → 转录校对 → 显示“模拟药A：资料从早上到晚上”“模拟药D：资料新增”“模拟药C：不变”等 → 老人逐项听 → 输出待与专业人员核实的问题清单。

**预期**：能找到所有差异，且整个过程不宣称真正修改实际服药计划。

## UC02 新资料没有列出旧药（必须展示）

新版是可能不完整的门诊记录，旧记录包含模拟药B而新记录未列出；程序只输出“新资料未提及B，需要核实是否继续”，不展示“停药B”的确定指令。

## UC03 相互矛盾/日期不明

两张资料中的同一种模拟药物单位、日期或药名不一致。该项进入 ambiguous，仍可在老人端解释“资料互相对不上”，但绝不生成可执行剂量/停药指令。

## UC04 无AI密钥或模型异常

后端有明显的运行状态；用户选择**显式虚构演示模式**或改手动录入。不能显示“AI已识别”同时实际偷偷用内置规则替代。

## UC05 老人不会拍照/不愿开麦

老人只按“找家人帮忙”，由演示角色切换到家属端完成；关闭语音时仍用文字与图形完成任务。拒绝麦克风授权不影响主流程。

## UC06 刷新/中途离开

同一浏览器恢复尚未完成的案例；需提示Demo存于本设备、不适合作为真实医疗资料库。

# 7\. 功能需求 / 用户故事与验收标准

## FR01 角色选择与切换 P0

• As 老人：我不必理解复杂身份管理，只想进入适合我的简单页面。  
• As 家属：我能快速定位“上传和核对资料”。  
• AC：进入任何页面始终可识别当前角色；演示中能一键切换；正式版真实授权实现保留为P1/后续。

## FR02 原始资料管理 P0

• 支持旧/新两版资料、来源、时间、文件状态；不可把药品包装上印的通用说明直接作为个人医生用药计划。  
• AC：缺失旧版、新版或关键日期时系统阻止“无警告地比较”；仍能生成明确待核实列表。

## FR03 AI 结构化提取 P0

• 服务端对接真实多模态/文本模型，或者提供清晰可插拔的 mock adapter；两者相互隔离。  
• 提取内容：名称、原始单位、剂量、频率、时间描述、明确“开始/停止”语句、文档日期、原文证据；缺字段保持 null。  
• AC：模型响应必须通过 schema 验证，不符合返回 extraction\_failed；原文证据必须可回溯；不补写未识别的药名/剂量。

## FR04 家属转录核对 P0

• 文档和字段对照；允许修正 OCR，记录谁何时改了哪个字段（Demo只需本地操作记录）。  
• AC：未解决的关键冲突无法以“全部已核实”绕过；并且转录核对只改变文本状态，不改变医疗确认状态。

## FR05 规则差异引擎 P0

• 对每条可匹配药物计算类别，保留旧值/新值/来源ID与冲突原因。  
• AC：缺省不判停药；名称/规格不确定时 ambiguous；相同字段 unchanged；明确可证实的变化 changed；增加或明确停止仍需标记专业核实边界。

## FR06 老人端语音说明＋卡片 P0

• 支持浏览器文本朗读（可用时），可停止/重复；不支持时清楚展示字幕。语音输入可作为P1增强。  
• AC：基本操作不依赖语音输入；语音不工作不阻断核对；卡片可键盘操作，保持语音与卡片内容一致。

## FR07 求助和待核实清单 P0

• 将冲突、含糊、起效日期缺失等汇总成可向医生/药师提问的句式。  
• AC：求助入口每个老人端任务页可见；没有伪造医生回复；复制/打印失败有可见反馈。

## FR08 本地历史 P0

• 维护多个资料核对记录和阅读进度，仅存于本浏览器的演示数据；清除/重置前有提醒。  
• AC：刷新不丢失最后一个有效案例；显示数据来源和是否为模拟。

## FR09 安全与隐私 P0

• 明确演示用途，不收集真实患者数据；开发示例一律虚构药名；API密钥不落客户端；有数据清除入口。  
• AC：页面不输出实际处方、诊断、真实吞服结论；所有无来源/冲突均转“待核实”；外部共享需用户主动触发。

# 8\. AI 工作流、数据契约与处理边界

## 8.1 工作流

用户任务与文件 → 内容安全预处理 → 模型文本/OCR提取 → JSON Schema校验 → 家属核对原文 → 规则差异引擎 → 简明语言模板/受约束LLM解释 → 老人语音和图形展示 → 待专业核实清单 → 记录与评测

**核心决定**：比较算法先用规则而不是让LLM自由输出比较结论；LLM负责非结构化提取和低复杂度表述。自由对话只做**任务意图识别＋导航**，不回答医学建议。

## 8.2 核心对象（建议 TypeScript，字段可加不可随意删）

### —— 数据契约或目录示例 ——

## 8.3 Diff 规则 V1

• 首先比较来自同一人、同一任务且具明确版本来源的两份文件；文档 completeness=unknown/partial 时自动保持高风险提示。  
• 标准化仅用于辅助比对：去空白、全半角、文本数字等；不得凭药品名称近似度把不同规格或不同成分当成同药。  
• 对完全可定位身份的条目，比较 strengthText / doseText / frequencyText / timeText / explicitAction / dates，输出字段级差异。  
• 旧有而新版未提及：missing\_in\_new；不推**断停止。**  
• 新版明确写“停用/停止”且能关联原文：explicit\_stopped，仍然输出“新资料明确写有停用信息，是否适用请向医生/药师核实”，不生成指令。  
• 新版出现无法可靠与旧版匹配的药物：若完整性和身份可靠才 explicit\_added，否则 ambiguous。  
• 日期不明确、冲突条目、单位缺失、扫描不清晰、混合多个病人的资料：ambiguous 并阻断安全应用动作。  
• 无任何显著变化时显示“本次**已比对的信息里**没有发现明确差异，不能据此判断用药方案一定没有变化”。

## 8.4 LLM 输入/输出约束

• 必须区分 ExtractPrompt 与 ExplainPrompt，都返回结构化对象。提取prompt要求只抽取出**现的字段、附原文证据、不推断停药、不自行换算剂量；解释p**rompt不得给临床建议、不得隐含已确认。  
• schema\_version 必填；验证失败要求重新解析一次或进入手工修正。异步调用要支持loading、取消、错误和重试，避免重复插入数据。  
• 模型不输出“99%可以安全服用”等无依据置信度；识别质量可用 clear / uncertain / unreadable 供UI表述。  
• 禁止将照片、完整原文、模型响应及API key 打到生产日志；基础演示只用虚构数据。真实数据场景需另行隐私、合规和安全评估。

## 8.5 语音边界

• P0：浏览器 speechSynthesis（若支持）朗读固定或受约束生成的文本，有一键停止、重听和字幕；不自动长期监听。  
• P1：SpeechRecognition / 兼容替代仅识别有限意图 start\_compare, repeat, next, previous, help, stop；识别为“药怎么吃/改多少”时必须进入安全说明而不是继续询问药物建议。  
• 不支持或拒绝麦克风：主流程保留完整按钮操作；禁止假装“正在聆听”。  
• 长句拆短；提示用户当前进度、何时可以回答；可反复播放，不自动超时跳页。老人端最好无背景音乐。

# 9\. 适老体验与视觉系统设计约束

## 9.1 视觉语言

• **不是儿童化或医院设备面板**：温暖中性的白/米白底，深色文字，少量暖色提示；品牌可暂用“安心药盒”。  
• 页面结构：移动端单列卡片、留白、清楚层级；桌面端可以出现资料与转录并列；避免一次展示十几条药品字段。  
• 基础字体：建议正文 **20–24 CSS px**，主要按钮字更大；保证长药名与数字不被省略、支持文本放大至200%仍可读。  
• 核心触控目标建议 **≥60×60 CSS px** 并留间隔，按最新具体设备测试；这是项目设计目标，不把CSS像素直接视为工信部dp/pt规范原单位。  
• 普通正文对比度目标≥4.5:1，图标/大字/控件边界遵循适用的WCAG标准；禁止仅凭红绿区分变化。  
• 图标＋文字＋语音一起说明 新增 / 调整 / 原文明确停止 / 未提及 / 需要核实，用法必须一致。

## 9.2 任务交互

• 老人屏幕每页尽量只有一件事、一到两个主要按钮；最重要的“重听”和“找人帮忙”固定可找。  
• 不依赖复杂手势、长按、双击、拖拽和悬浮提示；必须能键盘 Tab 操作，焦点可见，屏幕阅读器能理解按钮。  
• 避免医疗术语和机器状态词：不要讲“OCR提取置信度”，而讲“这几个字我没看清，请家人帮忙检查”。  
• 不使用“您操作错了”的责备语气；错误恢复要说明系统未完成的事，允许返回、重试与暂时退出。  
• 语音、屏幕提示双通道一致；语音不适合所有老人，因此不能作为唯一信息来源。  
• 用户无需自己拍摄；资料采集可以通过家属、文件导入、手动录入实现。

## 9.3 语音文案示例（只作为交互稿）

• 首页：“您好。医生给您换药了吗？您可以告诉我，也可以按下面的按钮。”  
• 等家属：“没关系，您不需要拍照。可以请家人帮忙把新药单放到这里。”  
• 资料变化：“这份新资料和之前的记录有一处不一样。我们一项一项看。”  
• 信息冲突：“这一项我没法确认。请不要只凭这个结果改药，我们把问题记下来问医生或药师。”  
• 全部完成：“我们已经整理好了资料变化和待核实问题。这是一份核对清单，不是新的服药指令。”

# 10\. 失败、降级与 Human Gate（不可省略）

情况　｜　系统处理　｜　不能发生的事情  
老人不懂拍照　｜　家属协助/手动录入/演示样例　｜　强制进入相机权限页  
新版纸张不完整　｜　明示“不能确认是否还有其他变更”，列缺失　｜　推断未提及的药停用  
OCR认错药名或看不清剂量　｜　字段标黄/待复核，展示来源位置，可手动修正　｜　AI 自行补全或擅自合并相似药名  
两份文档来源或日期冲突　｜　允许描述差异，但放入需专业确认；不应用方案　｜　依据“最新上传时间”认定医嘱有效  
新旧文档都没差异　｜　说“在已比对字段里未发现明确差异”　｜　宣称“药单绝对正确”  
麦克风权限拒绝　｜　大按钮照常使用　｜　页面一直转圈等待说话  
浏览器不支持TTS　｜　字幕/图标可完整完成操作，提示当前功能不可用　｜　页面无替代方式  
AI失败/超时/429　｜　展示错误及重试；可手工录入或主动选择模拟　｜　偷偷切换mock却显示真实AI成功  
用户问“我该吃多少”　｜　澄清产品边界，显示有效医嘱与专业求助路径　｜　自行给出剂量与服药建议  
家属要求“一键医生确认”　｜　不提供此按钮，提示需线下专业核实　｜　假造医师审核或电子签章  
异常状态记录丢失　｜　显示本地数据限制，允许重载样例　｜　虚构有云端备份

**Human Gate 1（转录）**：家属/用户确认识别文字与来源相符。**Human Gate 2（临床）**：现实中的医生或药师确认医疗正确性；演示系统无权替代。二者不能合成单一“确定”按钮。

# 12\. 工程实现建议（给 Codex）

## 12.1 技术推荐（可等效替代，但须说明理由）

• 前端：**React \+ TypeScript \+ Vite**，组件化路由与状态管理；CSS/Tailwind均可，优先清晰与响应式。  
• 前端验证：**Vitest**（diff和状态规则单测）＋**Playwright**（关键端到端流程）；基本可用性/键盘测试。  
• 后端：轻量 Node/Express 或可部署的 Serverless API，处理真实AI请求，**禁止将密钥写入前端**。  
• 持久化：首版用本地 JSON fixture \+ IndexedDB/localStorage（只保存最少案例数据，不持久存真实病历图片）。**不得宣传为跨设备同步/合规医疗存储**。  
• 数据验证：Zod/JSON Schema；差异引擎为独立纯函数；AI 适配器以 mock / real 明确切换。  
• 可运行与部署：提供 .env.example、README、npm run dev/build/test、一键情境切换；无真实模型凭证时 Mock Demo仍可运行。

## 12.3 开发阶段与完成定义

**S0｜项目搭建与视觉系统**：搭建响应式布局、老人/家属双角色路由、全局大字组件、语音朗读兼容层、静态样例。输出页面地图与截图。

**S1｜完整 Mock 闭环**：实现来源管理→字段校对→差异→老人逐卡→问题清单→历史；包含8个测试剧本；规则单测通过。**这一步必须可独立演示，不依赖AI服务。**

**S2｜真实 AI 接入**：接入服务端真实模型、解析JSON、来源证据、错误降级；对比真实与mock标识。没有配置密钥仍能使用示例，但UI不能谎称实际模型运行。

**S3｜适老与质量验收**：移动尺寸测试、桌面浏览器测试、键盘与语音降级、空态错误态、刷新恢复、至少核心流程端到端自动化；在没有实际老人时标明“模拟可用性走查”。

**S4｜提交展示**：可运行Demo地址/本地启动，README，截图，测试记录，已知限制，设计取舍，AI调用说明，可能用户研究计划；不可编造用户数据。

## 12.4 Definition of Done（最终必须满足）

• \[ \] 无API密钥也可完整运行 **Mock演示**，且顶部/案例页明确“演示数据”。  
• \[ \] 有可启用的 **真实AI服务端适配器**；UI清楚标注模式，真实调用成功/失败与mock不可混淆。  
• \[ \] 老人端 ≥6 个有真实路由与交互的任务页面（首页、发起、等待/总览、逐项、帮助、清单、历史等），家属端 ≥4 页；不是只有导航壳。  
• \[ \] DEMO-01\~08可复现，每个演示按钮有实际动作，刷新能恢复有效状态。  
• \[ \] diff引擎有单元测试：**新增/字段变化/未提及≠停药/显式停用/日期冲突/无法匹配**。  
• \[ \] 两种 human gate 明确，不能将“转录校对完毕”显示为“医嘱已获专业确认”。  
• \[ \] 老人端字体、触控目标、对比度、键盘焦点、语音失效降级符合第9节目标。  
• \[ \] 没有可被理解成药物诊断/处方推荐的生成内容，异常时明确求助医生/药师。  
• \[ \] 有构建、单测、端到端测试报告及可复现的安装运行指令；失败如实记录。

# 13\. 埋点、测试与研究回流

## 13.1 仅用于未来研究的匿名事件名（演示阶段可只输出本地计数）

## 13.2 三组可用性对照（未开展，不可写成结果）

• A 现有纸质新旧药单手工核对。  
• B 手工录入＋规则比较的非AI网页。  
• C AI提取＋规则比较＋语音图形辅助的网页。

测量：完成时间、理解并指出变化的正确率、危险遗漏、求助次数、是否意识到专业核实边界，以及主观负担。优先测试5–8名符合场景的老人（探索性可用性研究），并由至少一位药师/临床专业人员审核测试任务材料及安全标准。

## 13.3 真实产品上线前阻断条件

没有专业验证流程、隐私与数据合规评估、模型安全评估、真实用户可用性测试时，不得将Demo用于真实医嘱管理、自动执行或公共医疗推广。涉及真实健康数据的存储和传输需要另行专门设计与审查。

# 14\. 需要产品负责人后续判断的三个问题（Codex先按默认值开发）

1\. **语音输入优先级**：默认 P0 做可靠TTS朗读及实体按钮式操作，P1做可选STT，避免受浏览器权限限制拖累完整流程。若笔试明确要求真实语音对话，再上调。  
2\. **AI 模型和密钥**：默认提供可插拔服务端接口＋显式mock，真实模型在提供密钥后启用。必须能展示至少一个真实AI结构化提取能力，若评审要求在线真实调用。  
3\. **演示人设与身份**：默认中国独立生活老人、家属在同一台演示设备切换角色，不实现真实跨设备账户；如果评审特别看重协同，可在P1加模拟邀请和权限撤销，但不虚构真正远程同步。

这些是**可调整的产品取舍**，不是阻碍Codex先做S0/S1的待回答问题。
